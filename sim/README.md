โฟลเดอร์นี้เป็น **Python simulation + gain design tool เท่านั้น** (ไม่แตะ hardware/, firmware/,
README.md หลัก) — ใช้จำลองพลวัตของระบบ, ออกแบบ/ตรวจสอบเกนควบคุม, และวิเคราะห์ไอเดีย "jump-up"

## 1. สมการแบบจำลอง (model equations)

### 1.1 พิกัดและสัญลักษณ์

- `theta` (θ): มุมเอียงเฟรมจากแนวตั้ง (rad), **0 = ตั้งตรง**
- `theta_dot` (θ̇): อัตราการเอียง วัดจากไจโร (rad/s)
- `omega_w` (ω_w): ความเร็วล้อ **สัมพัทธ์กับเฟรม** (rad/s) วัดจาก FG tach ของมอเตอร์ (หารด้วย gear ratio แล้ว = ความเร็วที่ล้อจริง)
- `a`: คำสั่งความเร่งล้อ (สัมพัทธ์กับเฟรม) ที่คอนโทรลเลอร์คำนวณ (rad/s²) — นี่คือ **output ของกฎควบคุม**
- `omega_cmd`: ความเร็วล้ออ้างอิงที่ส่งให้มอเตอร์ไดรเวอร์ (rad/s) = ∫a dt (clamp ที่ ±ω_max)

### 1.2 พลวัตกลไก (Lagrangian derivation)

จุดหมุน (pivot) อยู่ที่ขาตั้ง U-frame. กำหนด:

- `I_b`: ความเฉื่อยของเฟรมรอบ **จุด CM ของตัวเอง** (ไม่รวม parallel-axis)
- `m_b`, `l_b`: มวลและระยะจากจุดหมุนถึง CM ของเฟรม (รวมมอเตอร์/แบต/บอร์ด)
- `I_w`: ความเฉื่อยของล้อรอบแกนหมุนของมันเอง
- `m_w`, `l_w`: มวลล้อ และระยะจากจุดหมุนถึงแกนล้อ

ให้ φ = มุมสัมบูรณ์ของล้อ = θ + ψ (ψ = มุมล้อสัมพัทธ์กับเฟรม, ψ̇ = ω_w)

พลังงานจลน์: `T = ½(I_b + m_b l_b² + m_w l_w²) θ̇² + ½ I_w (θ̇+ω_w)²`

พลังงานศักย์ (θ=0 ตั้งตรง เป็นจุด**สูงสุด**ของ V → ไม่เสถียร ตามธรรมชาติของ inverted pendulum):
`V = (m_b l_b + m_w l_w) g cos θ`

Euler-Lagrange ให้สมการ 2 ตัว (τ_w = แรงบิดที่กระทำต่อล้อ, แรงปฏิกิริยา -τ_w กระทำกลับเฟรม):

```
(I_b + m_b l_b² + m_w l_w²)·θ̈ = (m_b l_b + m_w l_w)·g·sin θ − τ_w      ... (1) เฟรม
I_w·(ω̇_w + θ̈) = τ_w                                                   ... (2) ล้อ (สัมบูรณ์)
```

รวมสองสมการเพื่อกำจัด τ_w (ใช้จำลองจริงใน `model.plant_deriv`):

```
C = I_b + m_b·l_b² + m_w·l_w²        (ความเฉื่อยรวม "ไม่รวม" ล้อหมุนรอบแกนตัวเอง)
B = (m_b·l_b + m_w·l_w)·g            (สัมประสิทธิ์แรงบิดโน้มถ่วงที่ทำให้ล้ม)

theta_dd = (B·sin(theta) − I_w·ω̇_w) / (C + I_w)
```

โดย `ω̇_w` มาจากโมเดลมอเตอร์ (ดู 1.3) — สมการนี้ไม่มี circular dependency เพราะ `ω̇_w` ถูกกำหนด
เป็น "servo ความเร็วสัมพัทธ์" ที่ไดรเวอร์ควบคุมเอง (ไม่ขึ้นกับ θ̈ ของเฟรมโดยตรง — สมมติว่า
ไดรเวอร์ทรงกำลังพอจะ regulate ความเร็วสัมพัทธ์ตามที่สั่งได้ ภายใต้ limit ของทอร์กสตอลล์)

**ทวนเช็ค:** เมื่อไม่มีแรงโน้มถ่วง (B=0) และไม่มีแรงภายนอก โมเมนตัมเชิงมุมรวม
`L = (C+I_w)·θ̇ + I_w·ω_w` ต้องคงที่เสมอ (ทดสอบใน `test_model.py::TestMomentumSanity`) — เพราะ
แรงบิดมอเตอร์เป็นแรงคู่ภายในที่หักล้างกันในระบบรวม (Newton's 3rd law)

### 1.3 โมเดลมอเตอร์+ไดรเวอร์ (1st-order + limit)

```
ω̇_w_desired = (omega_cmd − omega_w) / tau_m
ω̇_w = clip(ω̇_w_desired, −alpha_max, +alpha_max)

alpha_max = tau_stall_wheel / I_w
tau_stall_wheel = tau_stall_motor × gear_ratio × gear_eff
omega_max = (motor_no_load_rpm × 2π/60) / gear_ratio
```

`tau_m` (time constant ของลูปความเร็วภายในของไดรเวอร์ BLDC) **ไม่รู้ค่าจริง** — sweep 0.02-0.15s

### 1.4 เซนเซอร์

- **Complementary filter** (มุม): `theta_hat[k] = alpha·(theta_hat[k-1] + gyro_meas·dt) + (1-alpha)·accel_angle`, `alpha=0.98`
  ต้อง **seed ค่าเริ่มต้นจาก accel** ก่อนเริ่ม (ไม่ปล่อยให้เริ่มจาก 0 แล้วไล่ตาม เพราะระบบนี้ล้มเร็ว
  มาก — time-to-double แบบ open-loop ~0.1s เท่านั้น ถ้า filter cold-start ช้าจะไล่ตามไม่ทัน)
- **Gyro**: ใช้ค่าตรงเป็น θ̇ ที่ใช้ในกฎควบคุม (มี noise + bias คงที่ต่อการทดลอง)
- **FG tach** (ω_w): มี noise + quantization step (`omega_w_quant`)
- **Delay**: หน่วง 1 sample (คำนวณ `a` จากค่าที่วัดได้ในรอบก่อนหน้า) ตาม spec
- Sample rate ควบคุม: `dt_ctrl = 2ms` (500 Hz ตาม ESP32-C3 loop); physics step 0.5ms (RK4)

### 1.5 กฎควบคุม (ตรง contract กับ firmware, ห้ามเปลี่ยน)

```
a = Kp·theta + Kd·theta_dot + Kw·omega_w + Ki·integral(theta)
omega_cmd += a·dt_ctrl
omega_cmd = clip(omega_cmd, −omega_max, +omega_max)
if |omega_cmd| < deadband: omega_out = 0   else omega_out = omega_cmd
```

Anti-windup: หยุด integrate `integral(theta)` เมื่อ `omega_cmd` อิ่มตัว (saturated) และ error มี
เครื่องหมายเดียวกับทิศที่ทำให้อิ่มตัวมากขึ้น (conditional integration) + clamp `|integral|`

## 2. Sign convention (สำคัญมาก — อ่านก่อนจูนเกนจริง)

- `theta > 0` = เอียงไปทางที่ `sin(theta)` ทำให้ `theta_dd` เป็น **บวกมากขึ้น** (ทิศทางที่กำลังล้ม
  ต่อไปถ้าไม่มีอะไรหยุด)
- `a > 0` = สั่งเร่งล้อ **สัมพัทธ์กับเฟรม** ไปทาง `+` → ทำให้ `ω̇_w > 0` → ในสมการ
  `theta_dd = (B sinθ − I_w·ω̇_w)/(C+I_w)` เทอม `−I_w·ω̇_w` จะเป็น**ลบ** → หักลบ `theta_dd` ให้
  ลดลง → **ต้านการล้มไปทาง +**
- **ดังนั้น `Kp` ต้องเป็น "บวก"** (theta เอียง + → อยากได้ a > 0 มาต้าน) — ยืนยันด้วย
  `test_model.py::TestSignConvention` และการคำนวณ LQR (ดูหัวข้อ 3)
- `Kd` ก็ต้องเป็นบวกเช่นกัน (θ̇ > 0 หมายถึงกำลังล้มเร็วขึ้นไปทาง + → ต้องการ a มากขึ้นไปต้าน)
- `Ki` เล็กกว่ามาก (~0.01-0.25 เทียบกับ Kp,Kd ที่เป็นร้อย) — เกิดจากการมี coupling ระหว่าง θ̈ กับ
  ω̇_w ผ่านเทอม `I_w` ในสมการพลวัต
- **`Kw` เป็นบวกเช่นกัน (ค่า default ปัจจุบัน = +1.0)** — ยืนยันแล้วว่า `Kw` *เป็น* LQR output ที่
  design-able จริง (ไม่ใช่ค่าคงที่ที่ LQR "ดันคงที่" แบบ Kp,Kd — ดู `design_gains.py` ส่วน
  "Kw verdict" ที่สวีป `q_omega` แล้ว `Kw` เปลี่ยนตามอย่างมีนัยสำคัญ 0.14→1.0→2.2 เมื่อ
  q_omega=0.02→1.0→5.0) เครื่องหมายบวกของ `Kw` ทำหน้าที่เป็น "wheel-speed regulation" อ่อนๆ ที่
  ช่วยลดอัตรา drift ของความเร็วล้อเมื่อมี sensor bias คงที่ (ดูหัวข้อ 3.6 Bias-drift) — ไม่ควร
  ตีความ `Kw>0` ว่าเป็น "ตัวเบรกความเร็วล้อโดยตรง" อย่างง่ายๆ เพราะมันมีผลทางอ้อมผ่าน coupling
  กับ θ̈ ด้วย — ให้เชื่อผลจาก LQR (ผ่านการเช็ค eigenvalues แล้วว่าเสถียร) มากกว่าการเดาด้วย
  สัญชาตญาณ

## 3. การออกแบบเกน (LQR)

### 3.1 Linearization

รอบ θ=0 (`sinθ≈θ`), สมมติมอเตอร์ตอบสนองอุดมคติ (`ω̇_w ≈ a` โดยตรง, ไม่มี lag/limit — ใช้ตรวจสอบ
กับ nonlinear sim ทีหลัง):

```
state x = [theta, thetad, omega_w],  input u = a
dx/dt = [[0,1,0],[B/(C+I_w),0,0],[0,0,0]] x + [[0],[-I_w/(C+I_w)],[1]] u
```

**หมายเหตุ:** ถ้า augment state เป็น `integral(theta)` แบบตรงๆ (`z_dot=theta`) จะไปชนกับ
"โหมดที่ควบคุมไม่ได้" ของระบบนี้ (ตรงกับปริมาณอนุรักษ์ทางฟิสิกส์ `L=(C+I_w)θ̇+I_w ω_w`, ซึ่ง
`dL/dt=B sinθ` ไม่ขึ้นกับ `a` โดยตรง เพราะแรงมอเตอร์เป็นแรงคู่ภายในที่หักล้างกัน) ทำให้
`scipy.linalg.solve_continuous_are` หาคำตอบไม่ได้ (ไม่ stabilizable ในทางทฤษฎี) — แก้ด้วยการทำ
**leaky integrator**: `z_dot = theta − eps·z` (`eps=0.02` เล็กมาก) ให้โหมดนั้นเสถียรแบบอ่อนๆ
พอให้ ARE แก้ได้ โดยไม่กระทบความแม่นยำ steady-state อย่างมีนัยสำคัญในช่วงเวลาที่สนใจ

### 3.2 ผลลัพธ์เกน (nominal parameters, ดูหัวข้อ 5) — รันจริงล่าสุดจาก `py design_gains.py`

| Gain set | Kp [(rad/s²)/rad] | Kd [(rad/s²)/(rad/s)] | Kw [(rad/s²)/(rad/s)] | Ki [(rad/s²)/(rad·s)] | วิธีได้มา |
|---|---|---|---|---|---|
| **Robust** | +1137.40 | +144.30 | +1.0000 | +0.0387 | LQR (q_theta=400, q_thetad=4, **q_omega=1.0**, q_int=40, r=1) |
| **Soft (conservative)** | +634.46 | +64.97 | +1.0000 | +0.0077 | pole-placement ตรง, wn=4 rad/s, ζ=1 (ดูหัวข้อ 3.3) |

(`q_omega` เปลี่ยนจาก 0.02 → **1.0** เทียบรุ่นก่อนหน้า — เหตุผลเต็มอยู่หัวข้อ 3.6 Bias-drift:
q_omega เดิมเล็กเกินไป ทำให้ Kw เล็ก (~0.14) ซึ่งปล่อยให้ wheel speed ลอย/drift เร็วเกินไปเมื่อมี
sensor bias คงที่)

(ถ้าปรับ `params.py` ตัวเลขจะเปลี่ยน — ค่าข้างบนคือค่าที่รันได้จริง ณ พารามิเตอร์ nominal ปัจจุบัน
gear_ratio=2.5, tau_stall_motor=0.09 N·m — เช็คซ้ำได้เสมอด้วยการรัน `py -X utf8 design_gains.py`)

### 3.3 ทำไมเกนดูตัวเลขใหญ่ (Kp~1000)?

เพราะ `Aeff = C+I_w` ของระบบนี้ **เล็กมาก** (~0.02 kg·m², เฟรม+ล้อเบา) เทียบกับ `B` (~1.2 N·m/rad)
ทำให้ระบบล้มเร็วมาก (open-loop pole ≈ √(B/Aeff) ≈ 8 rad/s, time-to-double ≈ 0.1s) ต้องใช้ loop
gain สูงเพื่อดึงกลับให้ทัน — สอดคล้องกับความจริงที่ reaction-wheel pendulum ขนาดเล็กแบบนี้เป็น
โจทย์ควบคุมที่ "ไว" (ต้องการ sensor/actuator เร็ว)

### 3.4 ⚠️ ข้อจำกัดสำคัญ: งบแรงบิด (torque margin)

แรงบิดโน้มถ่วงที่ทำให้ล้ม ≈ `B·sin(theta)`:

- ที่ 5° ≈ 0.108 N·m
- ที่ 10° ≈ 0.215 N·m

แรงบิดล้อสูงสุดที่ทำได้ (nominal, gear_ratio=2.5, tau_stall_motor=0.09 N·m) ≈ **0.191 N·m**

→ ที่ **5° margin ≈ 1.8x (พอใช้)** แต่ที่ **10° margin ≈ 0.89x (< 1 !)** หมายความว่า **ต่อให้จูน
เกนสมบูรณ์แบบที่สุด ก็ไม่มีทางถ่วงดุลได้ที่ 10° นิ่งๆ** เพราะล้อสร้างแรงบิดต้านได้ไม่พอ — นี่คือ
ข้อจำกัดทางฮาร์ดแวร์ ไม่ใช่ปัญหาการจูนคอนโทรลเลอร์ (ดูผล Monte Carlo หัวข้อ 4 และกราฟ
`recovery_10deg.png`)

**ถ้าต้องการให้ recover ที่ 10° ได้จริง ต้องเพิ่ม `tau_stall_motor` (มอเตอร์แรงกว่านี้) และ/หรือ
เพิ่ม `gear_ratio` (แลกความเร็วสูงสุด)** — เนื่องจากขอบเขตโครงงานกำหนดแค่ 5° จึงไม่ใช่ปัญหาต่อ
การส่งงาน แต่ต้องระวังตอนทดสอบจริงไม่ให้ปล่อยเอียงเกิน ~7-8°

### 3.5 Feasibility vs Robustness Monte Carlo — **อย่าสับสนสองอย่างนี้**

รุ่นก่อนหน้าของไฟล์นี้รายงาน Monte Carlo แบบเดียว (เกน nominal ชุดเดียว ทดสอบกับพารามิเตอร์สุ่ม
**เต็มช่วง** RANGES) ซึ่งทำให้ตัวเลข success rate ต่ำผิดปกติ (~14%) และ**สับสน** ระหว่าง "ระบบ
ควบคุมไม่ดี" กับ "ไม่รู้พารามิเตอร์จริง" — ตอนนี้แยกเป็น 2 การทดลองที่ตอบคำถามต่างกันชัดเจน:

**(a) FEASIBILITY** — สุ่มพารามิเตอร์ **เต็มช่วง** RANGES (ทุกตัวพร้อมกัน) แล้ว **ออกแบบเกนใหม่
เฉพาะชุดนั้น** (เหมือนวัดพารามิเตอร์จริงมาแล้ว retune) → ตอบ "ถ้ารู้พารามิเตอร์จริงแล้ว จะทรงตัว
ได้ไหม" (N=100/มุม):

| θ₀ | success rate | saturated | settling time (สำเร็จ) | peak wheel rpm |
|---|---|---|---|---|
| 5° | **10.0%** (10/100) | 87.0% | mean 0.58s, max 0.93s | mean 980, max 1972 |
| 10° | **0%** (0/100) | 100% | — | mean 1367, max 2397 |

ตัวเลขนี้**ยังต่ำอยู่** แม้เกนถูก retune ต่อตัวอย่าง — เพราะ `sample_random()` สุ่มพารามิเตอร์
**ทุกตัวพร้อมกัน** เต็มช่วง ทำให้หลายตัวอย่างเจอ "โชคร้ายพร้อมกันหลายตัว" (เช่น gear_ratio ต่ำ
**และ** tau_stall_motor ต่ำ **และ** tau_m สูง พร้อมกัน) ซึ่งสะสมกันจนไม่มีทางแก้ด้วยเกนใดๆ (ข้อ
จำกัดทางฟิสิกส์จริง ไม่ใช่บั๊ก) — **นี่คือเหตุผลที่ต้อง**ดูหัวข้อ 3.7 (hardware_requirements.py)
ที่สวีป**ทีละตัวแปร**รอบ nominal แทน ซึ่งให้ภาพที่ actionable กว่ามาก (ผลออกมาสอดคล้องกับที่
คาดไว้: gear≥3 หรือ torque margin≥1.5x ให้ success ~95%)

**(b) ROBUSTNESS** — ใช้เกน **Robust ชุดเดียวคงที่** (nominal) ทดสอบกับพารามิเตอร์ที่คลาดเคลื่อน
จาก nominal แค่ **±20%** (ทุกตัวพร้อมกัน, ไม่ใช่เต็มช่วง) → ตอบ "เกนชุดนี้ทนความคลาดเคลื่อนจาก
การชั่ง/วัดระดับปกติได้ไหม โดยไม่ต้อง retune" (N=100/มุม):

| θ₀ | success rate | saturated | settling time (สำเร็จ) | peak wheel rpm |
|---|---|---|---|---|
| 5° | **68.0%** (68/100) | 29.0% | mean 0.63s, max 1.55s | mean 424, max 1864 |
| 10° | **2.0%** (2/100) | 98.0% | mean 0.74s, max 0.92s | mean 1544, max 1995 |

**สรุป:** ที่ 5° (ขอบเขตโครงงาน) เกน Robust ชุดเดียว (ไม่ retune) ทน ±20% mis-estimation ได้
**68%** ของเวลา — เพียงพอสำหรับต้นแบบที่จะวัดพารามิเตอร์คร่าวๆ ก่อนแล้วค่อย fine-tune บนบอร์ดจริง
ที่ 10° ทั้งสองแบบใช้ไม่ได้ (สอดคล้องกับ torque margin <1 ที่พบในหัวข้อ 3.4 — เป็นข้อจำกัดฮาร์ดแวร์
จริง ไม่ใช่เกน)

### 3.6 Bias-drift check: Kw ป้องกัน wheel speed ลอยได้แค่ไหนเมื่อ IMU มี offset คงที่?

**คำถาม:** ถ้า IMU มี systematic offset คงที่ (ไม่ใช่ noise สุ่ม — เช่น มุมติดตั้งเพี้ยน/ไม่ได้
calibrate accel ให้ดี) 0.5° ตลอดเวลา, `Kw` (ซึ่งเป็นบวกเหมือน `Kp`) ป้องกัน wheel speed ไม่ให้
ลอยไปเรื่อยๆ จนอิ่มตัว (saturate) ได้จริงไหม?

**พิสูจน์ทางคณิตศาสตร์ก่อน:** โมเมนตัมเชิงมุมรวม `L=(C+I_w)θ̇+I_w ω_w` มี `dL/dt=B·sinθ` **ไม่ขึ้น
กับ a โดยตรงเลย** (แรงมอเตอร์เป็นแรงคู่ภายในที่หักล้างกันในระบบรวม, ดูหัวข้อ 3.1) → โหมดนี้
**controllable ไม่ได้ด้วย feedback ใดๆ** (ข้อเท็จจริงทาง control theory: eigenvalue ของโหมดที่
ควบคุมไม่ได้ ขยับไม่ได้ไม่ว่าจะเลือก K อย่างไร) → **ถ้า θ_true ไม่ลู่เข้า 0 แบบสมบูรณ์ (θ_ss=0
เป๊ะ) wheel speed จะ "ลอย" (drift) ตลอดไปแบบ linear ไม่มีวันหยุด** ไม่ว่าจะจูน `Kw` เท่าไหร่

**ผลจำลองยืนยัน** (theta0=0, accel_bias=0.5°, deterministic, 120s):

| q_omega | Kw | θ_ss (ที่ 120s) | wheel speed @120s | drift rate | เวลาที่จะอิ่มตัว (ประมาณ) |
|---|---|---|---|---|---|
| 0.02 (เกนรุ่นก่อน) | 0.1414 | -0.0017° | -619.6 rpm | **-0.1438 rpm/s** | **~1.9 ชม.** |
| **1.0 (เกน default ปัจจุบัน)** | **1.0000** | -0.00004° | -95.2 rpm | **-0.0032 rpm/s** | **~130 ชม. (~5.4 วัน)** |

**สรุป:** `q_omega` เดิม (0.02) ให้ `Kw` เล็กเกินไป (0.14) → wheel speed ลอยเร็วพอจะอิ่มตัวได้ใน
เวลาไม่ถึง 2 ชั่วโมง ซึ่งเป็นปัญหาจริงถ้าทดสอบต่อเนื่องนาน — **จึงเปลี่ยน default เป็น q_omega=1.0
(Kw~1.0)** ซึ่งลดอัตรา drift ลง **>40 เท่า** (เวลาที่จะอิ่มตัวขยับจาก ~2 ชม. เป็น ~5 วัน) โดยแทบไม่
กระทบการตอบสนองที่ 5° (Kp เพิ่มขึ้นแค่ ~11%, peak rpm ปกติยังต่ำ) — **นี่คือ Kw ที่ design ได้จริง
ผ่าน LQR (`q_omega`), ไม่ใช่ค่าคงที่แบบ Kp,Kd** (ยืนยันด้วยการสวีป q_omega ใน `design_gains.py`
ส่วน "Kw verdict": Kw=0.14→0.45→1.0→2.24 เมื่อ q_omega=0.02→0.2→1.0→5.0 ในขณะที่ Kp,Kd แทบไม่ขยับ)

**ข้อควรระวังเชิงปฏิบัติ:** drift นี้เป็นฟิสิกส์ที่หลีกเลี่ยงไม่ได้ 100% (ไม่มีค่า Kw ใดทำให้เป็น 0
เป๊ะ) วิธีแก้ที่แท้จริงในระบบจริงคือ **calibrate IMU ให้ offset เข้าใกล้ 0 ที่สุด** และ/หรือถ้า
ต้องการรันต่อเนื่องนานมาก (หลายชั่วโมงขึ้นไป) ควรเพิ่มกลไก "momentum dumping" (bleed wheel speed
กลับ 0 เป็นระยะเมื่อ theta นิ่ง) ในเฟิร์มแวร์ ซึ่งอยู่นอกขอบเขตของ linear control law นี้

## 4. ไอเดีย Jump-up (Experimental)

แนวคิด: เฟรมนอนพักที่มุม `theta0` (~ -30 ถึง -45°), หมุนล้อขึ้น `omega_jump` แล้วเบรกภายใน
`t_brake` (0.05-0.2s) เพื่อถ่ายโมเมนตัมเชิงมุมของล้อ → เฟรม, หวังเหวี่ยงขึ้นตั้งตรง

**สูตรประมาณ** (โมเมนตัมเชิงมุมอนุรักษ์ระหว่างเบรกสั้นๆ):

```
theta_dot_f = I_w·omega_jump / (C+I_w)                      (ความเร็วเฟรมหลังเบรก)
ต้องการ:  ½(C+I_w)·theta_dot_f² ≥ B·(1−cos theta0)           (พลังงานพอขึ้นตั้งตรง)

=> omega_jump_min = sqrt( 2·B·(1−cos theta0)·(C+I_w) ) / I_w
```

**ผลจริง (nominal params, รัน `py design_gains.py`):**

| theta0 | omega_jump_min | rpm | ภายใน omega_max? | เวลาเบรกที่ต้องใช้จริง (alpha_max จำกัด) | ขึ้นถึงตั้งตรงจริงไหม (nonlinear sim) |
|---|---|---|---|---|---|
| -30° | 33.1 rad/s | 316 | ใช่ | ≥0.42s | **ไม่ถึง** (apex -64.9°) |
| -35° | 38.5 rad/s | 368 | ใช่ | ≥0.49s | **ไม่ถึง** (apex -76.0°) |
| -40° | 43.8 rad/s | 418 | ใช่ | ≥0.56s | **ไม่ถึง** (apex -81.7°) |
| -45° | 49.0 rad/s | 468 | ใช่ | ≥0.63s | **ไม่ถึง** (apex -82.8°) |

**ผลลัพธ์ (สำคัญ, ค้นพบที่ไม่คาดคิด):** ถ้าดูแค่ "ความเร็วที่ต้องการ" (`omega_jump_min` ~
316-468 rpm) เทียบกับ `omega_max` ของมอเตอร์ (1600 rpm ที่ gear=2.5, หรือ 4000rpm ที่ gear=1)
ดูเหมือน **feasible สบายๆ** — แต่ปัญหาจริงคือ **"อัตราการเบรก" ไม่พอ**: การเบรกจาก `omega_jump`
ลงมา 0 ภายใน `t_brake` ที่ต้องการ (0.05-0.2s) ต้องใช้ความหน่วง 190-770 rad/s² แต่ `alpha_max`
ที่ทำได้จริงจากทอร์กสตอลล์ที่สมมติมีแค่ **78 rad/s²** (ต่างกัน 3-10 เท่า!) → การเบรกใช้เวลาจริง
**~0.4-0.6s** ไม่ใช่ 0.05-0.2s ระหว่างนั้นแรงโน้มถ่วงมีเวลากระทำนานขึ้น (เฟรมยังเอียงมากอยู่)
ทำให้พลังงานที่ควรถ่ายเป็นการเหวี่ยงขึ้นกลับถูกใช้เสียไปกับการที่เฟรมยังคงล้มต่อระหว่างเบรก
(ผล nonlinear sim ยืนยัน: **theta_apex แย่กว่า theta0 เดิมเสียอีก** ในทุกกรณีที่ทดสอบ)

**สรุป (honest verdict): ไอเดีย jump-up แบบ "เบรกเร็ว 0.05-0.2s" ไม่ feasible ด้วยพารามิเตอร์
nominal ปัจจุบัน — คอขวดคือ "แรงบิด/อัตราเบรก" ไม่ใช่ "ความเร็วสะสมโมเมนตัม" ตามที่คาดไว้ตอนแรก**
ถ้าต้องการให้ใช้งานได้จริงต้อง:
1. เพิ่มทอร์กสตอลล์มอเตอร์ (หรือใช้เบรกกลไก/ไฟฟ้าที่แรงกว่าการหน่วงผ่านมอเตอร์ปกติ) เพื่อให้
   `alpha_max` สูงพอเบรกภายใน 0.05-0.2s จริง และ/หรือ
2. เพิ่ม `I_w` ของล้อ (มวล/รัศมีมากขึ้น, มวลกระจุกขอบ) ซึ่งลดทั้ง `omega_jump` ที่ต้องการ**และ**
   ความหน่วงที่ต้องการต่อ `t_brake` เดียวกัน และ/หรือ
3. ยอมรับ `t_brake` ที่ยาวขึ้น (~0.5s) แล้วออกแบบใหม่โดยคิดผลแรงโน้มถ่วงระหว่างเบรกด้วย (จะซับซ้อน
   ขึ้นและมักได้ผลแย่กว่าการประมาณแบบ "โมเมนตัมอนุรักษ์" ตรงๆ)

## 6. วิธี retune เมื่อรู้มวล/ความเฉื่อยจริง

### 6.1 สิ่งที่ต้อง "วัดจริง" บนชิ้นงาน (เรียงตาม impact ต่อผลลัพธ์)

| ต้องวัด | วิธีวัดที่แนะนำ | กระทบพารามิเตอร์ไหน |
|---|---|---|
| **ทอร์กสตอลล์มอเตอร์** (สำคัญที่สุด — ดูหัวข้อ 3.7) | datasheet BLDC-3640, หรือทดสอบจริง (ล็อกเพลา+วัดกระแส/ใช้ load cell) | `tau_stall_motor` |
| **gear ratio จริง** | นับฟันเฟือง/รอบสายพานจริง | `gear_ratio` |
| **motor step-response time constant** | ทดสอบสั่ง step speed แล้วอ่าน log FG (`motor_test`) หา τ ของการไต่ระดับความเร็ว | `tau_m` |
| **มวลเฟรม/ล้อ** | ชั่งจริงแยกชิ้น (เฟรม+มอเตอร์+แบต+บอร์ด กับ ล้อ) | `m_b`, `m_w` |
| **ตำแหน่ง COM (ความสูง pivot→CM)** | หาจุดสมดุล (balance point) ของเฟรมเมื่อวางนอนบนขอบมีด/แกน แล้ววัดระยะจาก pivot | `l_b` |
| **ตำแหน่งแกนล้อ** | วัดตรงจากแบบ/ชิ้นงานจริง | `l_w` |
| **โมเมนต์ความเฉื่อยล้อ `I_w`** | (ก) วิธี bifilar/trifilar pendulum แกว่งล้อแล้ววัดคาบ หรือ (ข) ถ้ามีไฟล์ CAD (Fusion 360) ใช้ mass properties ของโมเดลโดยตรง (แม่นกว่าประมาณจาก `k_w`) | `I_w` (แทนที่การประมาณจาก `k_w`) |

### 6.2 ขั้นตอน

1. วัดค่าตามตารางข้างบนให้ได้มากที่สุด
2. รันเกนสำหรับพารามิเตอร์จริงทันทีด้วย CLI (ไม่ต้องแก้โค้ด):
   ```bash
   py -X utf8 design_gains.py --set m_b=<...> l_b=<...> m_w=<...> l_w=<...> gear_ratio=<...> tau_m=<...> tau_stall_motor=<...> --quick
   ```
   จะพิมพ์ตารางเกน + ตรวจสอบเร็ว (N=20 ที่ 5°) + bias-drift check + `#define` พร้อมวางในเฟิร์มแวร์
3. ถ้าวัด `I_w` ได้ตรงๆ (bifilar pendulum หรือ Fusion mass properties) ให้แก้ `params.py::NOMINAL`
   ให้ `k_w` สะท้อนค่านั้น (`I_w = k_w * m_w * R_w**2` → คำนวณ `k_w` ย้อนกลับ) แล้วรัน `--set` ใหม่
4. ทดสอบบนบอร์ดจริงจากมุมเล็กๆ ก่อน (1-2°) แล้วค่อยขยับไป 5° เมื่อมั่นใจ
5. ถ้าสั่นหรือ oscillate ให้ลด Kp/Kd ลงพร้อมกันในสัดส่วนเดิม (ลอง 70-80% ของค่าที่ได้) ก่อนไล่
   ปรับทีละตัว — หรือใช้ gain set "soft" (`pole_placement_gains`, wn ต่ำกว่า) แทน

## 7. สรุปสำหรับทีม (verdict)

- **กฎควบคุม (control law) เป็นแนวทางที่ถูกต้อง** — sign convention ยืนยันแล้ว (หัวข้อ 2 + เทสต์),
  LQR design สม่ำเสมอ, ปิดลูปแล้วเสถียรเชิงเส้น (ดู eigenvalues ทุกกรณี) — **ไม่ใช่จุดเสี่ยงหลัก**
- **ความเสี่ยงจริงอยู่ที่ฮาร์ดแวร์ ไม่ใช่อัลกอริทึม:**
  - **torque margin** (ทอร์กสตอลล์มอเตอร์ × gear_ratio เทียบกับแรงบิดโน้มถ่วง) ต้อง **≥ 1.5x**
    ที่ 5° — ถ้าต่ำกว่านี้ **ไม่มีเกนไหนช่วยได้** (ข้อจำกัดทางฟิสิกส์ตรงๆ)
  - **`gear_ratio` ควร ≥ 3** และ **`tau_stall_motor` ควร ≥ 0.08 N·m** (ดูหัวข้อ 3.7)
  - **`tau_m` (motor lag) ต้อง ≤ ~0.08s** — ถ้าไดรเวอร์/มอเตอร์ตอบสนองช้ากว่านี้ ระบบพังทันที
    (0% success ในทุกการทดลอง) เพราะ loop bandwidth ที่ต้องการ (~8 rad/s) ชนกับ actuator
    bandwidth (1/tau_m) พอดี ไม่มี margin เหลือให้ noise/delay จริง
- **10° อยู่นอกขีดความสามารถของฮาร์ดแวร์ที่ประมาณไว้ทุกกรณีที่ทดสอบ** (0% success ทั้ง
  feasibility และ robustness Monte Carlo, torque margin <1 ที่ nominal) — **ไม่ใช่ปัญหาเพราะ
  ขอบเขตโครงงานกำหนดแค่ 5° อยู่แล้ว** แต่ต้องระวังไม่ปล่อยให้เอียงเกิน ~7-8° ตอนทดสอบจริง
- **Kw เป็นตัวแปรที่ design ได้จริงและมีผลจริง** (ต่างจาก Kp/Kd ที่ถูกบังคับโดยฟิสิกส์) — ใช้
  q_omega=1.0 (Kw~1.0) เป็น default ใหม่เพื่อลดความเสี่ยง sensor-bias-driven wheel drift ในการ
  ทดสอบที่รันต่อเนื่องนาน (ดูหัวข้อ 3.6)
- **ก่อนขึ้นบอร์ดจริง**: วัดพารามิเตอร์ตามหัวข้อ 6.1 (โดยเฉพาะทอร์กสตอลล์มอเตอร์และ tau_m — สอง
  ตัวที่กระทบผลลัพธ์มากที่สุด) แล้วรัน `design_gains.py --set ... --quick` เพื่อได้เกนที่เหมาะกับ
  ของจริง ไม่ใช่ใช้ nominal เดาๆ ตรงๆ
