# Reaction Wheel Balance

โครงตัว U ทรงตัวบนขอบฐาน (แกนเดียว) ด้วย **ล้อเหวี่ยงปฏิกิริยา** — มอเตอร์ BLDC เร่ง/หน่วงล้อเหวี่ยง แล้วแรงบิดปฏิกิริยาตามกฎอนุรักษ์โมเมนตัมเชิงมุมดันโครงกลับมาตั้งตรง อ่านมุมเอียงจาก MPU-6050 คำนวณด้วย state feedback บน Arduino แล้วสั่งมอเตอร์ที่ 500 Hz

โปรเจคนี้เป็นงานจริงที่ทดสอบกับฮาร์ดแวร์แล้ว — ตัวเลขทุกตัวในเอกสารนี้มาจากการวัด ไม่ใช่จากการจำลอง

## ผลลัพธ์ที่ทำได้จริง

| ความสามารถ | สถานะ | ตัวเลขที่วัดได้ |
|---|---|---|
| ทรงตัวต่อเนื่อง | ✅ ใช้งานได้ | > 2 นาทีโดยไม่ล้ม · ส่าย SD **0.27–0.34°** (ช่วง −1.4 ถึง +0.8°) |
| ลุกขึ้นเองจากท่านอน (jump-up) | ⚠️ ไม่เสถียร | สำเร็จ **3 ใน 8 (38%)** บนชุด Nano · เคยได้ 3/3 บนชุด Mega ที่บอร์ดอยู่นอกโครง |
| ต้านแรงผลัก | ~8° | มุมสูงสุดที่ดึงกลับไหว (กรณีล้อหยุดนิ่ง) |

ข้อสรุปสำคัญ: **ข้อจำกัดอยู่ที่กำลังมอเตอร์ ไม่ใช่การจูน** — มอเตอร์เร่งล้อได้จริงประมาณ 40 rad/s² น้อยกว่าที่โมเดลคาดไว้ประมาณ 3 เท่า ครั้งที่ jump สำเร็จมี duty ตัน 0% ของเวลาทุกครั้ง ส่วนครั้งที่ล้ม duty ชนเพดาน 21–44% ของเวลา

## หลักการควบคุม

คำนวณ **ความเร่งของล้อ** ไม่ใช่ PWM โดยตรง เพราะแรงบิดปฏิกิริยาเป็นสัดส่วนกับความเร่งของล้อ:

```
a = Kp·θ + Kd·θ̇ + Kw·ω + Ki·∫θ        →  สะสมเป็น ω_cmd  →  duty
```

- เกนทุกตัวเครื่องหมายบวกเหมือนกัน (ตาม LQR) และ **Kp มีค่าต่ำสุดประมาณ m·g·l / I_w** — จูนแบบเริ่มจาก Kp = 0 ไม่ได้
- ไดรเวอร์เป็น **voltage mode** ไม่ใช่ speed servo จึงชดเชย back-EMF เป็น `(ω_est + τ·a) / ω_fs`
- ค่าปัจจุบัน: `Kp 1137.4 · Kd 450 · Kw 3.0 · Ki 0.0387` (เก็บใน EEPROM ได้ ค่าใน EEPROM จะ override `config.h`)

## ฮาร์ดแวร์

| ส่วน | รุ่น | หมายเหตุ |
|---|---|---|
| คอนโทรลเลอร์ | **Arduino Nano** (ATmega328P) | เดิมเป็น Mega 2560 · เฟิร์มแวร์ build ได้ทั้งสองตัว |
| IMU | MPU-6050 (GY-521) | I2C · ใช้ accel `atan2(ay, az)` + gyro X |
| มอเตอร์ | BLDC-3640 + ไดรเวอร์ในตัว | อัตราทดมอเตอร์:ล้อ = 6 · FG ~70 พัลส์/รอบล้อ |
| ล้อเหวี่ยง | จานโลหะ 20 cm | |
| ไฟเลี้ยง | 12V (3S Li-ion + BMS) + ฟิวส์ 3A | ต่อตรงเข้ามอเตอร์ ไม่ผ่าน buck |

**ขาที่ใช้** (จาก `config.h`) — PWM `D9` บน Nano / `D11` บน Mega · DIR `D7` · BRAKE `D6` · FG `D2` (INT0, `INPUT_PULLUP`) · ปุ่ม jump `D4` · IMU ผ่าน I2C

> ⚠️ **ปิดไฟ 12V ทุกครั้งก่อนแฟลชหรือรีเซ็ตบอร์ด** — PWM กลับขั้ว (raw HIGH = หยุด) ถ้าขา PWM ลอยหรือ LOW มอเตอร์จะวิ่งเต็มสปีดทันที

> ⚠️ **ห้ามใส่ R pull-up ภายนอกที่ขา FG** — ทดสอบ A/B แล้ว ใส่ 4.7k ไป 5V นับพัลส์ได้แค่ ~60/100/70 ต่อวินาที เทียบกับ 187/421/645 เมื่อถอดออก ใช้ `INPUT_PULLUP` ของบอร์ดอย่างเดียว

## เริ่มใช้งาน

```bash
# คอมไพล์ + อัปโหลด (ปิดไฟ 12V ก่อน!)
arduino-cli compile --fqbn arduino:avr:nano firmware/reaction_wheel_balance
arduino-cli upload  --fqbn arduino:avr:nano -p COM8 firmware/reaction_wheel_balance
```

ลำดับ bring-up กับเครื่องใหม่ (ห้ามข้าม):

1. `imu_test` → หาแกนและเครื่องหมายของ IMU ใส่ใน `config.h`
2. `motor_test` (ยึดล้อให้แน่น/ถอดล้อก่อน) → หา polarity ของ PWM/DIR/BRAKE, นับพัลส์ FG
3. `step_test` → วัด step response ของมอเตอร์ (t63, rpm สูงสุด)
4. `sign_test` → ยืนยันทิศของแรงบิดปฏิกิริยา
5. วัดมวล/COM/ความเฉื่อยล้อจริง → `py -X utf8 sim/design_gains.py --set … --quick` → ได้เกน
6. `reaction_wheel_balance` → `zero` → `start`

**คำสั่ง serial** (115200 baud): `start` `stop` `zero` `save` `get` `help` · `kp/kd/kw/ki/sign [v]` แก้เกนระหว่างทรงตัวได้ · `jump [rpm] [kick_ms] [capture_deg] [rate_dps]` และ `jumpcfg` · `tel 0|1` เปิด/ปิด telemetry CSV · `selftest`

เครื่องมือช่วย: `tools/imu_viewer.html` — เปิดในเบราว์เซอร์ที่รองรับ Web Serial ได้กราฟ real-time, ปุ่ม Start/Stop/Jump/Zero, แก้เกน และบันทึก CSV

## ข้อค้นพบที่ใช้เวลากว่าจะได้มา

- **FG มีพัลส์หลอก** ห่างกัน 25–35 µs ตอนกลับทิศ ทำให้อ่านความเร็วล้อได้ 30,000–42,000 rpm แล้ว duty ชน 100% ไปผิดทางประมาณ 300 ms → กรองด้วย `FG_MIN_PERIOD_US` 700 µs และให้ตัวประมาณความเร็วยึดโมเดลเป็นหลักแล้วค่อยปรับตาม FG
- **จูน Kd คือจุดที่ได้ผลมากที่สุด** — Kd 300 → SD 1.59°, Kd 500 → SD 0.34° (ดูตารางเต็มใน `tuning/balance_gains.md`)
- **ตอนรับช่วงจาก jump ต้องหรี่พจน์มุมลง** — Kp ที่มุม 8° สั่งความเร่ง ~160 rad/s² จากมอเตอร์ที่ทำได้ ~40 คือสั่งเกินกำลัง 4 เท่า ล้อจึงอิ่มตัวทันทีแล้วเหวี่ยงเลยไปอีกฝั่ง แก้ด้วยการไล่ระดับ Kp ขึ้นใน 350 ms (`CAPTURE_BLEND_MS`)
- **กติกาส่งต่อดูที่ความเร็ว ไม่ใช่มุมอย่างเดียว** — เตะจนอัตราเอียง > 90 °/s → ปล่อยไหล → ส่งต่อเมื่อ |θ| ≤ 8° และอัตราเอียง 60–90 °/s ทำให้ผลขึ้นจาก 3/10 เป็น 3/3 ในชุดนั้น
- **บทเรียนเรื่องวิธีวัด** — ระหว่างการจูนมีการตั้งกฎจากข้อมูลชุดเล็กแล้วพังเมื่อเจอข้อมูลใหม่ถึง 3 ครั้ง (ที่ชัดที่สุด: "ต้องมีล้อหมุนค้าง ≥ 90 rpm ตอนรับช่วง" แยกข้อมูล 15 ครั้งแรกได้สมบูรณ์แบบ แล้วได้ 2/8 กับชุดใหม่) ตัวแปรที่วัดได้ทุกตัวทับซ้อนกันมากระหว่างครั้งที่สำเร็จกับล้ม → กฎใหม่ต้องมีอย่างน้อย 20–30 ตัวอย่างและยืนยันกับชุดข้อมูลที่ไม่ได้ใช้ตั้งกฎ

## ข้อจำกัดและขั้นต่อไป

ตอนทรงตัวปกติ เอียง 2° ใช้ duty ไปแล้ว 0.25 → มุมสูงสุดที่ดึงกลับไหวประมาณ 8° และนั่นคือกรณีล้อหยุดนิ่ง แต่ตอนรับช่วงจาก jump จริงมีทั้งมุม 6–8°, อัตราเอียง 40–60 °/s และล้อที่หมุนค้างอยู่ — รวมแล้วเกินกำลังมอเตอร์ ระบบจึงทำงานอยู่บนเส้นแบ่งพอดี

**ปรับพารามิเตอร์ไปไม่ถึง 99% บนฮาร์ดแวร์ชุดนี้** ต้องแก้ที่ตัวเครื่อง เรียงตามที่น่าจะได้ผล:

1. ลดมวลบนโครงโดยเฉพาะส่วนบน (ย้ายบอร์ด/แบตลงต่ำหรือออกนอกโครง)
2. เพิ่มความเฉื่อยล้อ — แลกกับการปั่นล้อช้าลง ต้องวัดจริงก่อน
3. เพิ่มกระแสจากแหล่งจ่าย

ยังค้าง: วัด I_w, มวล และ COM จริง เพื่อให้ sim ตรงกับเครื่อง (ตอนนี้ sim ประเมินเกินจริง — คาดว่า 200 rpm พอสำหรับ jump แต่จริงต้อง 550)
